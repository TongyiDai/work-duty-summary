# 采集口径与命令 Playbook

**默认全量采集**下列全部重要飞书资产，它们都是反推职责的一等信号，无主次取舍。命令 shortcut 以各依赖 skill 的 SKILL.md / `lark-cli <domain> --help` 为准；本文件给口径、顺序与实测过的坑，不硬编码可能过期的 flag。执行前按对应 skill 的渐进式发现规则确认命令真实存在。

时间窗默认近 6 个月，落到显式区间（例如 `2026-02-17 ~ 2026-08-17`）。

## 通用原则

- 默认 `--as user`。读取前核验 `identity=user` 与租户。先 `lark-cli contact +get-user --as user` 拿到**本人 open_id**，后续多处命令要显式传。
- **缺权限先征询，不静默降级**：某类资产因 scope 缺失读不到时，告诉用户这是重要信号，问是否 `lark-cli auth login --scope <缺失scope> --as user` 补授权后重采；用户不补才降级并标注。**例外**：只读演练 / 无人值守 / 批处理模式下，不阻塞等待——默认降级并在报告显著标注"此处本应征询补授权"，让用户事后决定是否补跑。
- **默认脱敏**：证据台账只记"来源类型 + 时间 + 职责线索"，不存聊天/邮件/文档正文、收入成本客户人员等敏感原文与数字。
- **串行 + 退避**：批量读取易限流，串行调用、失败退避重试，不并发轰炸。
- 每类资产采集完，在证据覆盖报告里记：是否纳入、时间窗、拿到多少条、缺失及原因。

## 自评/述职/总结类文档（lark-drive / lark-doc）

反推职责的**最强信号**：很多人把绩效自评、述职、晋升材料、H1/H2 总结、工作复盘写成飞书云文档，本人亲手写了"我做了什么、拿了什么结果、对齐哪些目标"。飞书**绩效系统 OpenAPI 一般拿不到授权**（实测 `/open-apis/performance/v2/semesters` 报 `need_user_authorization`），所以主路径是搜本人写的这类文档，用现有文档权限就能拿到。

1. `drive +search --created-by-me --query "<关键词>"`（`--as user`）分别搜：`绩效总结`、`自评`、`述职`、`晋升`、`晋级`、`答辩`、`H1总结`、`H2总结`、`工作复盘`、`重点工作产出`、`能力提升计划`、`OPDCA`、`环评` 等。
2. 命中后读标题；判断确为本人自评/总结的，可 `lark-doc` 读正文，提取**本人陈述的职责与结果**（不落敏感数字与他人评价）。

**时间窗放宽**：自评/述职/晋级材料天然低频，最完整的往往是上一考核周期（近 6 个月外）写的。**这一类单独放宽到近 12 个月**，别被默认 6 个月窗口挡掉最强信号；用其内容佐证职责，同时在证据里标注文档日期。

**bitable 承载**：本人"近期重点工作/花名册/场景表"常是多维表格（bitable），`lark-doc` 读正文会报 `Unsupported document type 'bitable'`。命中 bitable 时**只取标题、不强读正文**，或改用 `lark-base` 读表；不要因读不到正文就丢弃这条信号。

**判定是否本人自评的启发式**（关键，见下"关键区分"）：优先信任 **标题含本人姓名 + owner=本人 + 第一人称叙述体正文** 的文档；标题带"员工/客户/方案参考/策略/沟通"等泛化词的，默认归客户方案而非本人自评。

**关键区分（实测：混淆风险很高）**：搜这些词会同时命中"本人的自评/总结"和"本人给客户做的绩效/晋升方案"。实测某次"能力提升计划"搜到 12 条里仅 1 条是本人的，其余全是客户方案——**纯靠关键词，客户方案会淹没本人自评**。判定规则：只有满足"**标题含本人姓名** 或 **正文第一人称写'我做了什么'**"才计入本人自评；标题带"员工/客户/方案参考/策略/面谈/沟通"等泛化词的，归入"我主编的文档 → 专业领域"，别当自评。

**隐私**：这类文档含敏感评价、等级、薪酬关联。台账只提炼"职责与结果线索"，不落等级/评分/薪酬/他人评价原文。

**可选加强（一般不可用）**：若环境恰好有绩效 scope，可用 `people-cli api GET /open-apis/performance/v2/semesters` 取周期→本人绩效活动→`review_datas`（自评/述职）。默认拿不到授权，不为它中断主流程；参数以 `people-cli schema` 与 `--dry-run` 为准。

## OKR（lark-okr）

反映本人主动承诺推动的目标与纵向承接关系——职责最强信号之一。

1. `okr +cycle-list` 列周期。**实测：该命令强制要 `--user-id <本人 open_id>`**，不带会报 validation 错误；先从 `contact +get-user` 拿 open_id 显式传入。
2. 选与时间窗重叠的周期（按起止日期重叠判断，不默认年度周期），`okr +cycle-detail` 读 O/KR。
3. 按需：`okr +progress-list` 看进展，`objective.alignments list` 看对齐关系（承接谁、被谁承接 = 纵向利益相关方）。

**常见坑**：user 身份常缺 `okr:okr.period:readonly`。按通用原则征询补授权；这是职责最强信号，值得补。提取每个 O 的方向、KR 的结果域、被 @ / @ 他人的协作对象。

## 任务（lark-task）

反映本人实际在做、对谁负责的具体事项。

- "我负责的 / 分配给我"：优先 `+get-my-tasks`。
- "与我相关 / 我关注 / 我创建"：优先 `+get-related-tasks`（按 `--assignee/--creator/--follower` + 本人 open_id 过滤）。
- 有明确关键词时才用 `+search`。

按时间窗过滤，提取：反复出现的任务主题、任务清单归属、协作成员。**高频固定任务**（如"XX 进展四周更新""到期报风险"）是职责节奏的强信号，聚成职责线索；一次性杂事忽略。

**实测坑**：任务接口无服务端时间过滤参数，`+get-my-tasks` 会返回全量（数百条）。**先拉全量再本地按 `created_at >= 窗口起点` 过滤**。注意 `created_at` 是 **ISO8601 字符串**（如 `2026-08-07T17:41:06+08:00`），不是毫秒时间戳，解析用 `fromisoformat` 而非除以 1000。

## 会议 + 妙记（lark-vc / lark-minutes）

反映参与/主持的议题、协作面、话语权。

- `lark-vc` 搜历史会议、看参会人快照与纪要（总结/待办/章节）。
- `lark-minutes` 搜妙记、读产物主题。
- **实测：`minutes +search` 返回的 `display_info` 是一整段富文本（含 `&lt;b&gt;` 等 HTML 转义），没有独立 topic/start_time 字段。** 取主题需切 `display_info` 首行并去标签，开始时间从 `meta_data.description` 里抠。

提取：高频会议/妙记主题（= 职责域候选）、常协作对象（= 利益相关方）。主持/召集 > 单纯参加。

## 日历例会（lark-calendar）

反映常规例会与固定协作节奏。看时间窗内高频/周期性日程主题，识别固定例会（= 常态职责与协作关系）。妙记已覆盖大部分会议信号时，日历主要用于补齐"没留纪要的固定例会"。

**实测**：`calendar +agenda` 按周取样即可识别固定循环例会（如双周会、每周上新、每日进展）。注意返回的 `data` 是 list 不是 dict，且 agenda 视图里 `start_time` 可能为空——解析时做防御，靠 `summary` 归纳主题。

## 我主编的文档（lark-drive / lark-doc / lark-wiki）

反映产出物与专业领域。

- `drive +search --created-by-me`（或等价的 `--mine`）列本人为 owner 的文档。
- **实测坑（字段路径）**：结果在 `data.results`，但**标题/时间/owner/token 都在每条的 `result_meta` 子对象里**——`result_meta.title`(或 `title_highlighted`，带 `<em>` 高亮和 HTML 转义需去标签)、`result_meta.token`、`result_meta.create_time_iso`、`result_meta.owner_name`；顶层同名字段常为 `None`，别读顶层。默认 page-size 只有 15，`data.total` 可能远超时间窗（如 395），且 `--created-since/--created-until` 对 total 无效——**必须用 page_token 显式翻页，采集后本地按时间窗二次过滤**，别信 total。
- **剔除噪声**：归纳前先滤掉无语义标题（`temp_markdown.md`、`Untitled Base`、`Untitled document`）。更要警惕**导入型批量**：同日大批量、统一前缀（如某次 200 篇 `BCG｜…`/`Bain｜…`/`McKinsey｜…` 抓取文章同日创建）是一次性资料导入，不代表本人产出领域，识别到"同日成批 + 统一前缀"就整批排除。
- 需要判断主题时 `drive +inspect` 解析 wiki 节点。读标题/类型/更新时间即可，不必读全文。

提取：持续产出的文档主题 = 专业领域职责。一次性文档忽略。

## 审批（lark-approval）

反映本人发起/审批的事项 = 职权边界与常态流程。看时间窗内高频审批类型（发起的 = 我要推动的事；审批的 = 我有决策权的域）。仅取类型与频度，不落敏感表单内容。

**实测**：`approval tasks query` 的已办/知会类型（如 topic 1/2/17/18）能拿到数据，高频审批类型是有效职权信号。但**"已发起"这条路契约不稳**：`tasks query` 的 topic 3 可能报 `field validation failed`，`instances initiated` 对时间戳参数要求严格（成对、单位敏感）。拿不到"已发起"时，用"已办/知会"的类型频度替代，并标注该限制，不要卡死。**审批数据无法按时间窗精确过滤**（跨全时段），只作"职权边界"的定性信号，不按窗口量化。

## IM 高频协作（lark-im / lark-contact）—— 隐私最敏感

反映高频沟通的群与人 = 利益相关方。**默认纳入**（本人数据、自助分析），但**只做频度/对象聚合，不读消息内容语义、不落原文**。

- 用 Feed 置顶、高频群、常联系人推断协作关系强度。
- `lark-contact` 把高频对象解析成姓名/部门，用于利益相关方标注（点名到人需脱敏或经确认）。

**实测坑**：`feed-shortcut-list` 的 detail 富化、`chat-list --sort active_time` / `--page-all` 在部分环境返回空，置顶明细拿不到。兜底：用默认 `im +chat-list`（首页约 20 个群）的群名/主题做聚合，并用任务/文档里"IM 跟进""某群同步"类线索侧证协作对象。IM 本就是弱信号层，接口不配合时如实标注"信号偏弱"，不强求。

用户明确不同意纳入 IM 时才跳过，仅用其余资产。

## 证据覆盖报告

采集结束在草稿里给一段覆盖说明：每类资产是否纳入、时间窗、拿到多少条证据、哪类缺失及原因（缺权限/未授权/无数据）。让用户知道结论建立在多少真实数据上、还有哪些重要资产没覆盖到。
